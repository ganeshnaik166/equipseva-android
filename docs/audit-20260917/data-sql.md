### DS-01 [HIGH] Every server timestamp is parsed with `Instant.parse`, but PostgREST emits `+00:00` offsets — on Android 8-13 (minSdk 26, no core-library desugaring) all `parseInstantOrNull()` results are null; notifications never leave the unread state
- File: app/src/main/kotlin/com/equipseva/app/core/data/notifications/NotificationDto.kt:41-42 (plus RepairJob.kt:103-110, RepairBid.kt:35-36/47-48, ChatConversation.kt:22-23, ChatMessage.kt:24-25, CostRevisionDto.kt:33 — 13 call sites; helper at core/util/Dates.kt:59-60; app/build.gradle.kts:66)
- What: `parseInstantOrNull()` is `runCatching { Instant.parse(it) }.getOrNull()`. PostgreSQL/PostgREST render `timestamptz` as `2026-05-04T13:00:00.123456+00:00`. `Instant.parse` (ISO_INSTANT) only accepts a literal `Z` on OpenJDK 8/11-based runtimes (fix JDK-8166138 landed in JDK 12); Android API 26-30 ship OpenJDK 8 libcore, API 31-33 OpenJDK 11 (unless an ART Mainline update back-ported 17). `minSdk = 26` and no `coreLibraryDesugaring` is configured anywhere in the Gradle config, so on those devices every DTO->domain instant is silently null: `Notification.readAt == null` => `isUnread == true` for every row forever (badge never clears, mark-read looks broken), `RepairJob.createdAtInstant/startedAtInstant/completedAtInstant`, bid/chat/cost-revision timestamps all null. Unit tests and the API-34+ emulator run on JDK >= 17 where `Instant.parse` DOES accept offsets, which is why this has never been observed.
- Evidence: Kotlin `fun String?.parseInstantOrNull(): Instant? = this?.let { runCatching { Instant.parse(it) }.getOrNull() }` and `readAt = readAt.parseInstantOrNull()` / `val isUnread: Boolean get() = readAt == null`. SQL contract: `RETURNS TABLE (... sent_at timestamptz, read_at ...)` / `RETURN to_jsonb(v_revision)` (20260504130000_propose_decide_cost_revision_rpcs.sql:115) — Postgres JSON encodes timestamptz with an explicit `+00:00` offset. The codebase already knows this: core/util/RelativeTime.kt:20-22 "OffsetDateTime.parse accepts both `Z` (UTC) and offset (`+05:30`) forms that Postgres timestamptz can emit". DatesTest.kt:20-23 only covers the `Z` form.
- Fix: `fun String?.parseInstantOrNull(): Instant? = this?.let { runCatching { OffsetDateTime.parse(it).toInstant() }.recoverCatching { Instant.parse(it) }.getOrNull() }` (ISO_OFFSET_DATE_TIME handles `Z`, `+00:00`, `+05:30` and 6-digit fractions on every API level). Same change in `Dates.prettyDate/prettyDateTime/isWithinDays/daysUntil` and features/chat/ChatScreen.kt:787/794.
- Test: DatesTest: `"2026-05-11T07:42:00.123456+00:00".parseInstantOrNull() == Instant.parse("2026-05-11T07:42:00.123456Z")` and the `+05:30` form; NotificationDto test: row with `"read_at":"2026-05-11T07:42:00+00:00"` maps to `isUnread == false`. Because JVM tests pass on JDK 17 with EITHER implementation, also pin with a connected test on an API 26-30 `eqs` image (or a JUnit rule that fails if `Instant.parse` is referenced from Dates.kt).
- Owner: ME

### DS-02 [MEDIUM] Re-placing a bid after withdrawal is impossible: `RepairBidInsertDto.status` is never serialized and the bid UPDATE policy's USING requires `status = 'pending'`, so the upsert's ON CONFLICT path raises an RLS violation (shown as KYC copy; outbox drops the bid)
- File: app/src/main/kotlin/com/equipseva/app/core/data/repair/SupabaseRepairBidRepository.kt:65-68; RepairBidDto.kt:27-34
- What: `placeBid` upserts on `(repair_job_id, engineer_user_id)`. `status` has a default (`"pending"`) so with `encodeDefaults=false` it is omitted from the payload. When the engineer's previous bid on the job is `withdrawn` (the flow the server comment calls "withdraw and submit a new one"), the INSERT conflicts and takes the `DO UPDATE` path; PostgreSQL evaluates the UPDATE policy USING against the existing (`withdrawn`) row and, for ON CONFLICT DO UPDATE, a USING failure is an error, not a skip -> HTTP 403 `42501` -> `toUserMessage` renders "You don't have access to this yet. Try again after KYC is verified." for a verified engineer; `RepairBidOutboxHandler` -> `classifyOutboxError` 4xx -> GiveUp (queued bid silently lost). Even if the policy were relaxed, the row would keep `status='withdrawn'` because status is not in the payload.
- Evidence: Kotlin `val status: String = "pending"` (default => omitted) + `client.from(TABLE).upsert(payload) { onConflict = "repair_job_id,engineer_user_id"; select() }`. SQL 20260703200000_round278_bid_update_allow_withdrawn_transition.sql: `FOR UPDATE ... USING (auth.uid() = engineer_user_id AND status = 'pending') WITH CHECK (... (status = 'pending' AND created_at > now() - interval '24 hours') OR (status = 'withdrawn'))`.
- Fix: make `status` a required (no-default) field so `"status":"pending"` is always on the wire (same rationale as `RepairJobInsertDto.status`), and ship a migration widening the policy to `USING (auth.uid() = engineer_user_id AND status IN ('pending','withdrawn'))` with WITH CHECK allowing `withdrawn -> pending` (reset `created_at` in a trigger so the 24h edit window restarts). Until then, map the RLS-USING 403 to "You already withdrew a bid on this job; contact support to re-bid".
- Test: serialize `buildRepairBidInsert(...)` with the exact SupabaseModule Json config and assert the JSON contains `"status":"pending"`; PGlite test: insert pending -> update withdrawn -> upsert again succeeds and reads back `pending`.
- Owner: ME

### DS-04 [MEDIUM] `markRead`/`markAllRead` write the DEVICE clock into `read_at`; the server guard rejects `read_at > now() + 1 minute` with 42501, so any phone whose clock runs >60 s ahead can never mark a notification read (and the outbox GiveUps the retry)
- File: app/src/main/kotlin/com/equipseva/app/core/data/notifications/NotificationRepository.kt:83-95, 98-121
- What: The client sends `read_at = Instant.now().toString()` (and `is_read = true`). The BEFORE UPDATE guard raises when the timestamp is more than a minute in the server's future. Clock skew of minutes is common on low-end Android; the failure is mapped to the KYC copy ("You don't have access to this yet…") and `NotificationReadOutboxHandler` -> `classifyOutboxError` treats the 4xx as permanent (`GiveUp`), so the read receipt is lost rather than retried.
- Evidence: Kotlin `set("read_at", Instant.now().toString()); set("is_read", true)`. SQL 20260425001745_notifications_baseline.sql:102-103 `IF NEW.read_at IS NOT NULL AND NEW.read_at > now() + interval '1 minute' THEN RAISE EXCEPTION 'notifications.read_at cannot be in the future' USING ERRCODE = '42501'`.
- Fix: stop sending `read_at` from the client (send only `is_read = true`) and extend `notifications_guard_user_update` with `IF NEW.is_read AND NOT coalesce(OLD.is_read,false) AND NEW.read_at IS NOT DISTINCT FROM OLD.read_at THEN NEW.read_at := now();` (or clamp: `NEW.read_at := least(NEW.read_at, now())`).
- Test: repository test with an injected clock 5 min ahead asserting the PATCH body has no `read_at`; PGlite test: UPDATE with `read_at = now() + interval '10 minutes'` succeeds and stores `<= now()`.
- Owner: ME

### DS-05 [MEDIUM] Room/SQLCipher: `DbPassphraseStore.getOrCreate()` silently rotates the passphrase when the sealed key cannot be unwrapped, but `provideDatabase` never wipes the existing encrypted `equipseva.db` — every subsequent open fails with "file is not a database" until the user clears app data

### DS-08 [LOW] Repair-feed search interpolates the raw query into PostgREST's `or=(…)` filter grammar; `sanitizeForIlike` escapes LIKE wildcards but not the grammar delimiters, so a search containing `,` `(` or `)` yields PGRST100 and an errored feed
- File: app/src/main/kotlin/com/equipseva/app/core/data/repair/SupabaseRepairJobRepository.kt:40-47, 254-255

- Fix: emit the pattern double-quoted per the PostgREST grammar: `"\"%" + needle.replace("\\", "\\\\").replace("\"", "\\\"") + "%\""` after the LIKE escaping (or strip `,()"` from the needle).
- Test: `sanitizeForIlike("GE, Philips (new)")` produces a value with no bare `,`/`(`/`)`; a fake-client test asserts the encoded `or` param round-trips.

- `StorageRepository.upload()` re-encodes JPEGs on every call (non-idempotent), so a caller that pre-hashes prepared bytes cannot satisfy `RepairPhotoDeliveryDao.markUploaded`'s `receipt.sha256 == contentSha256` if it routes through `upload()`; the v5 delivery DAO has no production caller in this snapshot, so this is latent only.
