### AN-01 [HIGH] Client can never revoke or re-claim an FCM device token: `DELETE` on `device_tokens` is revoked server-side and both client DELETEs swallow the 42501
- File: app/src/main/kotlin/com/equipseva/app/core/push/DeviceTokenRegistrar.kt:56-78, 89-104; supabase/migrations/20260428320000_security_revoke_delete_grants.sql:29; supabase/functions/send_push_notification/index.ts:324-329
- What: `revoke()` (sign-out) and `register()`'s "strip any other user's claim" both issue PostgREST `DELETE` on `device_tokens` as `authenticated`. Migration 20260428320000 runs `REVOKE DELETE ON public.device_tokens FROM authenticated, anon` and no later migration re-grants it or adds an RPC (grep: zero `GRANT DELETE`/`unregister*` hits). Every call fails with 42501 inside `runCatching` — silently. The server fan-out selects tokens by `user_id` only, so after A signs out (or B signs in) on the same device, A's pushes — including chat previews rendered as tray notifications — keep landing on that device until the token itself rotates. If the table has a unique key on `token`, B's upsert additionally 23505s and B never receives pushes on a device A used.
- Evidence: `supabase.from("device_tokens").delete { filter { eq("user_id", userId); eq("token", cachedToken) } }` wrapped in `runCatching` (revoke, 93-101); `.from("device_tokens").select("id, token").eq("user_id", notif.user_id)` (index.ts:324-327); `REVOKE DELETE ON public.device_tokens FROM authenticated, anon;` (migration :29). The migration's rationale says "No client-side DELETE path is legitimate today" — it did not account for this one.
- Fix: add a SECURITY DEFINER RPC `unregister_device_token(p_token text)` (`delete where user_id = auth.uid() and token = p_token`) and `claim_device_token(p_token text)` (delete rows for that token owned by other users, then upsert for `auth.uid()`); call them from `revoke()`/`register()`; surface failures via CrashReporter instead of bare `runCatching`. Defense-in-depth on the client: drop incoming pushes in `EquipSevaMessagingService` when `supabase.auth.currentUserOrNull() == null` or when a payload `user_id` != current user.
- Test: `DeviceTokenRegistrarTest` with a Ktor MockEngine returning 401/`42501` for `DELETE /rest/v1/device_tokens` — assert `revoke()` reports failure (today it cannot be observed); a migration lint test asserting every table the app DELETEs from (`grep "\.delete {"` in app sources) still has `GRANT DELETE` or an RPC.
- Owner: ME
