## 1. Architecture decisions

1. A person has one authenticated identity, potentially several legitimate memberships. The three public registration choices describe the intended first workspace: **Biomedical engineer**, **Hospital owner / manager**, **Engineering organisation / team administrator**. They are not three independent authentication systems. Existing users choose **Sign in**, then their permitted workspace if there is more than one.
2. **Platform owner** is a separately provisioned privileged identity, not a fourth public signup option. The paid organisation administrator never receives `profiles.role = 'admin'`, founder access, service-role credentials, or cross-tenant visibility. Payment buys organisation capabilities; it cannot buy platform privileges or verification.
3. Reuse `organizations` as the business entity where its verified schema supports the organisation type. Add membership/entitlement relationships to that entity after a schema census. Do not create a parallel customer/company universe just to draw a third tile. Names below are proposed, not claims that these tables exist.
4. A workspace is an operating context: personal engineer practice, a hospital organisation, or an engineering service organisation. A hospital's relationship with an engineering company is an explicit service agreement/job assignment, not membership that reveals all hospital data. Independent engineers keep a personal workspace; changing employment must not transfer private work, documents, or earnings to an employer.
5. Keep approved lime/ink surfaces, Space Grotesk headings and Inter body. Role/workspace distinctions use names, icons and labels; colour alone never identifies permissions or verification.
6. India state/UT and district are required structured selections for people, hospital sites and organisation offices/service areas. No map, location permission or coordinate is required for registration or discovery. Physical service addresses remain private textual job information for authorised participants. No claim that district selection proves attendance.
7. Demo is a clearly labelled synthetic sandbox with no production jobs, payouts, external messages, or real patient/hospital data. It must not be a shared-password account. The launch decision is a disposable client-local demo. A separately isolated demo backend is a deferred architecture decision, not an alternative enabled by this plan; simply adding `is_demo` to production queries is not an adequate isolation boundary.
8. Start with one managed team subscription per engineering organisation; seat/usage limits and price are server policy, not hardcoded mobile constants. Hospital/individual core access is not silently put behind this new organisation subscription. Commercial pricing and payment channel are release decisions after the applicable store/payment rules are verified.

## 3. Proposed data model and authorization contract

Before writing SQL, inventory actual `pg_catalog` definitions in an approved non-production copy: organisations/types, grants, policies, triggers, helper definitions, unique indexes, profile references, chain functions, storage paths, RPC signatures, service-role callers and existing billing tables. Record hashes and migration ledger. Source migrations alone do not prove their accumulated deployed state. If an equivalent production primitive exists, extend it with explicit compatibility tests.

Proposed additions, names subject to that inventory:

| Entity | Required contract |
|---|---|
| `organization_memberships` | `(organization_id,user_id)` unique; role/capabilities, active/suspended/removed status, verification requirements, membership version, audit timestamps. Separate organisation owner from mutable managers. Retain removed records/audit as policy requires; do not hard-delete history through user deletion cascades. |
| `membership_site_scopes` | Explicit membership-to-site grants with permission subset and scope revision; composite FKs prove the membership and site belong to the same organisation. Empty scope denies site access. Hospital owner has explicit organisation-wide scope; managers have delegated sites; hospital biomedical staff have assigned service/equipment tasks only. Server checks site scope for rows, attachments, jobs, exports and realtime. An engineering service relationship grants its job slice, not a hospital staff membership. |
| `organization_invites` | Organisation, verified target identity channel, hashed high-entropy token, intended least-privilege role, inviter, expiry, single-use/revoked/accepted status. Raw invite secret never appears in listing responses/logs. Partial unique constraint for active pending invite where appropriate. |
| `organization_service_areas` | Organisation plus canonical state/district IDs; independent engineer coverage uses the equivalent engineer-owned association. Base office is distinct from districts served. Require valid district-state pairs. |
| `organization_subscriptions` | Organisation, provider/channel, immutable provider customer/subscription IDs, plan version, billing interval, state, paid-through/trial/grace timestamps, cancellation timing, reconciliation version. No authenticated direct writes to authoritative fields. |
| `billing_events` / entitlement ledger | Provider event ID unique, payload hash, observed order/sequence, processing outcome; accepted entitlement revision. Receipts/webhooks update transactionally and idempotently. Never log entire sensitive payloads by default. |
| `organization_audit_events` | Actor, tenant, action, resource, before/after policy-safe details, request ID, immutable server time. Redact secrets and restrict exports. Include support/owner privileged access reasons. |
| Region reference tables | Stable source IDs, state parent, labels/aliases, validity/effective dates, dataset version. Historical jobs retain their location snapshot even if a district changes name/boundary. |

Every tenant-bearing resource must have an authoritative owner/tenant column or an unambiguous FK chain to one. Job participation can span the hospital and contracted engineering organisation, but grants exactly the shared job slice. The job carries commissioning hospital organisation, servicing party, assigned individual and explicit payment beneficiary snapshot; active profile/workspace changes cannot rewrite these facts.

Organisation authorization evaluates **identity + current active membership + permission + resource tenant/site/participation + applicable entitlement + resource state**, server-side, for reads, writes, realtime, storage and exports. A **personal engineer workspace** instead requires authenticated user ID equal to its immutable personal-owner ID plus role, verification and resource checks; it does not require an organisation membership or team-software subscription. Never convert a rejected organisation context into a personal one. Test independent engineer success with no company membership and denial of another person's personal workspace, alongside foreign-organisation denials. `active_workspace_id` from the client is a requested context, never proof of access. Stale JWT claims alone are insufficient to preserve revoked membership indefinitely; privileged mutations consult authoritative membership/revocation state.

- RLS uses `USING` for existing-row access and `WITH CHECK` for the proposed owner/tenant. Reparenting a job/document/member to a different tenant is a separate audited operation, not a normal UPDATE.
- SECURITY DEFINER RPCs validate `auth.uid`, membership, capability, object ownership and state inside the mutation transaction; set a safe search path, qualify relations, narrow EXECUTE grants and avoid trusting user-supplied actor IDs. Elevated workers still validate their claimed job/attempt and tenant; service-role bypass does not substitute for business checks.
- Protect membership, verified status, tier, monetary ledger and owner columns from broad client writes. Storage object paths and short-lived URLs must use the same resource access policy; knowing a UUID or filename is not authority.
- Payment entitlement is required for new subscription-only management operations. It must not erase access required to settle existing jobs, inspect receipts, handle disputes, cancel billing, export authorised data or close the account. Exact restricted-mode behavior belongs to the master plan.
- Owner account: strong MFA/step-up for bank/privilege changes, short-lived privileged session, server permission checks, reasoned audit trails and recoverable emergency access. No owner ability to read passwords, retrieve stored card secrets or silently impersonate accounts. Routine support gets a narrower separate grant.

## 4. Membership, invitations and dual affiliations

**Invitation acceptance:** logged-in verified recipient sees organisation identity, requested role, terms and disclosure scope. Server validates token hash/expiry/recipient, inviter's current authority, organisation status, seat/plan policy and existing membership; it consumes the token and creates membership atomically. Duplicate accept is idempotent. Revoked/expired/wrong-account tokens reveal no private organisation roster. Seat reservation/claim is serialized to avoid simultaneous over-allocation. A forged link never bypasses these checks.

**Removal/suspension:** take effect at the server immediately; increment membership revision, invalidate application context/realtime subscriptions and prevent queued writes. Keep assigned active work in a reassignment/settlement queue; do not silently delete jobs or confiscate personal earnings. Client receives a clear access-change page with safe workspace selection. Cached tenant data becomes inaccessible and is selectively purged. An already-issued public export URL must not remain a long-lived access bypass.

**Ownership transfer:** current owner and accepting eligible successor both authenticate freshly; lock organisation ownership row, verify successor membership and acceptance, preserve at least one owner, audit and notify both. Do not equate subscription payment-method owner with organisation owner. Lost-owner recovery uses an evidence-reviewed platform procedure, not a manager self-promotion endpoint. Subscription continuity and bank-beneficiary changes are separate transactions.

**Multiple affiliations:** an engineer may keep personal practice and join a service team. Initially allow several invitations/memberships but one explicit operating workspace per job/bid. A team manager sees only team work, not the engineer's private jobs, other teams' chat, KYC originals or personal bank data. A hospital employee who is also an engineer must not self-approve their own bid, completion, rating or payout; server rules identify the underlying user/beneficial relationship, not merely different workspaces. Conflicts require reassignment or an independently authorised approver. Public ratings follow real completed engagements; team ownership changes do not rewrite them.

## 5. Subscription state machine and payment boundaries

Retain provider billing lifecycle separately from the canonical derived app access **Pending / Active / Grace / Restricted / Suspended**. Cancellation at period end is a flag plus paid-through timestamp, not immediate denial. Use the transition/precedence contract in [security and payments](SECURITY_PAYMENTS_AND_ABUSE.md): invalid identity/membership and security suspension override payment; grace requires authoritative server/provider evidence. A payment callback in Android only means “confirmation pending.” Server receipt verification/provider webhooks plus reconciliation determine paid-through and entitlement revision. Duplicates, reordered events, refunds, chargebacks and delayed success cannot extend access twice or roll a newer terminal state backwards. Persist idempotency keys before external side effects and reconcile uncertain outcomes before retrying charges.

There is no live free trial at launch; the demo is client-local synthetic fixtures and does not require a bank/card. Any future live trial requires a separately reviewed eligibility/quota policy. Do not charge automatically without clear recurring-payment consent. Show total charge, interval, tax treatment where applicable, renewal/cancellation terms and receipt path before payment. Current payment/store requirements must be verified separately before implementation and before launch.

Seat changes use a server plan version and effective date; prorations are provider/server decisions. A removed engineer retains personal identity and authorised historical receipts. When a team subscription expires, no new paid management tasks are admitted, but safe completion/support/refund obligations survive under explicit capabilities. Payment suspension and fraud suspension must have different recovery copy and permissions.

Existing blockers stay visible: S1 account-cleanup races; S3 same-account navigation recovery; payout late-response downgrades after webhook success (M1); transient provider error encoded as HTTP 400 (M3). Candidate AMC proof-retention and SLA fixes do not close those remaining backend/session defects. No new paid team product goes live on an unreconciled ledger.

## 6. Session, workspace and offline ownership

Use one immutable operation context captured before the first suspension: authenticated user, observed login generation, workspace ID, workspace generation, membership revision and operation/idempotency ID. Exact Kotlin names are implementation decisions; reuse `SessionOwner` rather than inventing a second competing auth observer. Workspace generation changes on a context switch even for the same user. The server separately validates current permission; local generations prevent stale UI/device mutations, not authorization attacks.

Remote revocation denies new server requests immediately; disconnected devices only learn it on reconnection. Follow the bounded offline-lease contract in the security plan: no new offline privileged authority, encrypted owner-scoped cache, finite read/work lease, revalidation at foreground/reconnect and denial of queued stale writes. Local expiry/clock-restart behavior needs tests. Previously viewed or exported data cannot be recalled; no instant offline erasure promise is made.

Hospital site scope requires its own version in operation contexts. Test an otherwise-valid hospital member guessing a different site in the same organisation, site removal while an attachment request is suspended, mismatched membership/site foreign keys and an empty delegated-site set. Billing/organisation identity access does not implicitly expose every site's patients, equipment or service work.

- All pending requests/results, saved-state keys, Room rows, DataStore envelopes, drafts, photo stashes, notification taps, navigation entries, realtime leases and background jobs declare ownership. A late A response cannot publish into B or another workspace; cancellation alone does not prove safety for noncooperative code.
- Capture the departing ticket synchronously before any draft persistence, lock acquisition or network call. Cleanup deletes only that ticket's data at the actual mutation boundary. Final SDK logout must be owned too, so an old logout cannot invalidate the next login.
- Namespace Room/DataStore/cache state by user and workspace as appropriate. Introduce an additive Room migration; migrate only rows with provable owner and quarantine ambiguous legacy outbox/payment rows instead of replaying them under the current account. Server reconciliation remains the source of truth for money.
- Outbox has owner/workspace, operation key, kind, payload version, attempt/next-attempt time and expiry; query eligible rows for the active authorized context, not a global oldest-25 batch. Reject removed-member writes at drain time. Keep per-tenant fairness, bounded retry/backoff and a visible actionable failed state; do not label an authorization failure as “will sync later.”
- Outbox acknowledgements mark/delete only the claimed row/version. Photo/evidence uploads retain the resource owner through stash, worker and registration. Subscription/seat/beneficiary changes are online-only; offline data entry can produce clearly labelled drafts without committing privileges or money.
- Workspace switching cancels owned work, fences results, clears navigation and resolves a new server capability snapshot before showing the destination. It does not log out the whole identity or globally erase other legitimate workspace drafts.
- Define failed/cancelled logout recovery explicitly: either complete local logout or create a fresh owned recovery context after server validation. Never re-enable the old buffered links/leases simply because profile reload returned Ready.

## 7. Location migration without maps

Canonical region IDs and a versioned offline picker replace free text. Resolve existing exact labels/known aliases in a dry run; ambiguous/obsolete names go to a correction queue, never to a guessed district. Enforce foreign-key state/district pairing server-side. When state changes, reset an incompatible district. Show service area separately from home/private address. Engineers may select additional districts with bounded counts; ordering is deterministic and search remains usable for large lists.

Introduce a versioned district-based discovery RPC with pagination and eligibility filters; do not call the radius RPC with fabricated coordinates. Ranking should use district coverage, required skill, verified capability, availability and transparent response/work history; paid team membership is not a verification badge. Return minimal public profile fields, not home addresses.

Replace mandatory GPS check-in with a specific **arrival/evidence protocol** before removing the old requirement: the assigned engineer requests arrival, the authenticated authorised hospital contact confirms a short-lived job-bound challenge, required evidence is uploaded under a job-owned lease, and the server atomically records arrival/attendance. Rate-limit attempts, expire/consume challenges, prevent engineer/team self-confirmation, and bind photo registration to the job/session. A hospital contact can still collude; this is risk reduction, not proof of physical presence. Unavailable contact or network leads to an explicit provisional/service-support path without automatic payment release. Completion and money release require a separate acceptance step. Preserve old coordinate fields/history during migration; no silent zero/NULL workaround to bypass existing guards.

## 8. Scale, cost and load gates

Use existing Supabase/Postgres and Android architecture until measurements justify extra services. No per-tenant database or microservice split is required for the first release. Introduce indexes only from access paths and query plans: active membership `(user_id,status,organization_id)`, tenant membership `(organization_id,status,user_id)`, scoped jobs `(hospital_org_id,status,updated_at,id)` and servicing equivalent, service-area `(district_id,organization_id)`, invite token hash unique, provider event ID unique, subscription organisation/status, outbox owner/workspace/next-attempt. Avoid a new index for every filter combination.

Paginate job lists/chat/audit/export results with stable cursor ordering; fetch a compact workspace/capability bootstrap in one request. Use aggregated counters rather than N+1 lists, per-workspace realtime topics and lifecycle-aware subscriptions. Debounce location searches locally; bundle/cache a versioned region dictionary. Cap image dimensions/decoded bytes/count before upload, use resumable owned work where supported, signed private access and retention rules. Rate-limit OTP, invitation, search, exports, disputes and payment attempts by meaningful account/tenant/device/network signals, with legitimate recovery.

Before pilot, seed synthetic datasets at proposed planning tiers (100 organisations/1,000 people, 1,000/10,000, then 10,000/100,000 if business demand warrants). Measure p50/p95/p99 response time, DB query/lock time, pool saturation, outbox drain delay, memory, API errors and monthly cost. These are test tiers, not current user counts or promised capacity. Define release thresholds from baseline measurements; observe worst-case popular districts, large teams, simultaneous seat accepts, webhook bursts and reconnect storms. Performance tests must prove RLS remains effective under pagination/caches; speed cannot justify bypassing tenant filters.

## 10. First implementation slice: owned logout foundation

Recommended first code milestone remains S1 because adding workspaces magnifies an already reproduced cross-account deletion bug. This slice does **not** add paid roles, SQL entitlements or a third live dashboard.

1. Preserve the three failing `SignOutCleanupLocalBoundaryRegressionTest` cases and ordinary cleanup control. Add deterministic barriers for same-user re-login and cancellation while a storage lock is held. Capture one immutable departing login ticket before the first suspension.
2. Route every logout entry point (root gate, profile, account deletion and payout onboarding) through the same owned coordinator; fence admission/results synchronously. Stage the actual mutation APIs in bounded commits: owned outbox transaction, owner-keyed payment markers/prefs/stash, owned token revoke and SDK logout, per-topic realtime lease removal. A precheck followed by global `clearAll()` is explicitly insufficient.
3. Use real Room transaction tests and real DataStore transforms where those boundaries can suspend. Simulate A -> B, A -> signed-out -> A, A -> B -> A, process restart and noncooperative late completion. Show B's rows/payment proof/drafts survive; show A's old workers cannot recreate them after cleanup. Ordinary A cleanup and a fresh valid B enqueue/drain must still work.
4. Integrate root-session/router recovery tests for failed and cancelled logout so a valid renewed A context can receive new links without replaying old ones. Record any still-unobserved SDK identity boundary as an explicit limitation; do not claim total isolation from flow tests alone.
5. Run targeted tests, full units, lint, design ratchet, debug, unsigned release and applicable screenshot checks on the exact candidate. Record build-slot ownership before Gradle. Independent critic and QA each review the bounded changed scope and evidence; target >=9.5 without assigning an app-wide score. Do not hide known failures in a passing filter.

Next bounded feature slice after safety gates: a **read-only workspace bootstrap plus three-intent registration shell behind a feature flag**, with a synthetic organisation demo and canonical region picker. It must be possible to choose/preview the third persona without granting a live paid privilege. Before real membership creation, prove cross-tenant SELECT/INSERT/UPDATE/DELETE, forged role/workspace/plan, invite replay/race, last-owner removal, seat race, expired subscription and revoked-member tests in the database harness. Only then wire the smallest real organisation create/invite/accept flow.

If the coordinator starts a smaller preparatory coding step immediately after this plan, a safe independent boundary is **intent and region draft types only**:

- New `app/src/main/kotlin/com/equipseva/app/features/auth/PublicRegistrationIntent.kt`: three public intentions, stable non-privileged keys, no platform-owner option, no cast/mapping of engineering organisation to the global admin role. Unknown keys fail closed. This type is not an authorization claim and cannot itself create a membership.
- New `app/src/main/kotlin/com/equipseva/app/core/data/location/RegionSelectionDraft.kt`: pure state transitions using the existing region catalog; changing state invalidates an incompatible district, selecting a district requires its parent, blank/unknown choices remain incomplete. Do not assert the old dataset is current or use substring matching as proof of canonical identity.
- New focused tests under matching `app/src/test/kotlin` packages: all three intentions round-trip; admin/founder/unknown keys rejected; a forged district/state pairing cannot complete; state changes/reset/restore cannot preserve incompatible district; a valid ordinary selection works. The domain type can explicitly represent an incomplete legacy value without granting completion.
- No edits to `UserRole`, auth repositories, root routing, `SessionPresentation` or SQL for this preparatory step. A UI consumer comes in a later gated slice, and this preparatory commit is never reported as a shipped third-role workflow. S1 remains the priority enabling milestone; completing these pure types does not lower any security blocker.
