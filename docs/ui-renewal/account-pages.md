## Selected design language and shared rules

- The master `docs/UI_THEME_PAGE_PLAN_2026-09-12.md` governs the exact paired palette and shapes: primary lime `#C6FF00`, ink, and soft-white surfaces. Lime marks the main action, selected option, and limited emphasis; pair it with explicitly defined dark foreground. Black/soft-white form the reading surfaces. Keep destructive/error/warning/information roles distinct with text and icons; never recolor every status as success-like lime.
- Page headings: Space Grotesk, 28sp / 34sp line height, weight 600. Body: Inter, 16sp / 24sp, weight 400. Labels: 14–16sp / weight 600. Support: 12–14sp / weight 400 or 500. These are proposed tokens, not fonts currently bundled: `designsystem/theme/Type.kt:21` uses SansSerif, `Typography.kt:9` uses Default, and no `app/src/main/res/font` directory was found. Plan explicit Hindi/Telugu script fallback and inspect actual glyphs before accepting the font migration.
- Each page has one clear title, a short purpose, current status where material, grouped content, and one primary action. Use restrained outlined secondary actions. Put security/destructive operations in a separate section rather than equal-weight decorative cards.
- Plan normal, disabled, focused, selected, saving, error, empty, offline, stale-data, and success variants before implementation. Measure rendered foreground/background contrast for text and controls in both themes; preserve the existing 4.5:1 normal-text and 3:1 control-visibility planning gates. Do not infer these from token names.
- Every field has a persistent label, precise error, appropriate keyboard, and a route to recovery. Primary pill actions have 52dp minimum height; all other targets are at least 48dp. Master shape roles are cards 24dp, heroes 28dp, inputs 16dp. Text can wrap at 200% font scale. Sticky actions must clear IME/navigation insets. Support copy must not shrink below the selected 12sp floor. Reference specimen wording is not a repeated page title.
- Keep server-confirmed role, account, verification, payment, and submission states authoritative. A saved local draft, queued request, accepted upload, submitted review, and verified identity are different states.
- Owner/session/generation must scope editable state, async completions, picker results, and navigation callbacks. Retain form state only for the same login; a role or account switch must not reuse another owner's text, documents, snackbar, pending mutation, or navigation entry. These are design/implementation acceptance requirements; this source inventory does not establish every existing feature already meets them.
- Back closes the topmost menu/sheet first, returns to the originating page second, and never circumvents required root setup. Define save-in-flight and unsaved-edit behavior explicitly; do not invent durable draft support for forms that do not currently persist drafts.

## Source notation and reachability

For compactness, `F/` expands to `app/src/main/kotlin/com/equipseva/app/features/`, `N/` to `app/src/main/kotlin/com/equipseva/app/navigation/`, and `DS/` to `app/src/main/kotlin/com/equipseva/app/designsystem/`, under the repository above. Every source reference below is a function declaration or the exact nested callsite, not a runtime observation. `Main:123` means `N/MainNavGraph.kt:123`; `Auth:123` means `N/AuthNavGraph.kt:123`.

**Reachability classes:** active entry = visible entry or automatic root binding found; registered = composable route exists, without proof of a current menu entry; nested = a modal/step/component mounted by another page; legacy/inert = implementation or historical route remains without a current screen binding. A registered route is not proof of authorized access: authorization and deep-link admission remain separate implementation gates.
