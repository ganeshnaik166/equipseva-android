## Five concrete gaps and smallest regression-driven next steps

### 1. Unresolved role enters an engineer-shaped workspace; signup role-write failure has no recovery

**Source-verified:** `NeedsRole` falls into main at cold start (AppNavGraph:125) and counts as auth success (291–301). Main tabs default null/non-hospital to engineer (MainNavGraph:111–112), Home also uses an else engineer branch. Session's signed-in bootstrap performs token registration before profile bootstrap (SessionViewModel:56–79); its initial false bootstrapping value means state sequencing also deserves a cold-start test. We have not demonstrated a visual flash on a device.

Signup `addRole` failure is only reported to Crashlytics, then form clears, analytics fires and navigation effect emits (SignUpViewModel:129–156). No visible role-retry state is provided by that block.

**Next:** first add navigation/session regression cases for cold-start and fresh-login NeedsRole, profile-fetch failure with no confirmed role, failed addRole, stale cached role, and out-of-order sign-in/profile completion. Then introduce explicit role resolution/retry and confirmed-role selection before a workspace; preserve authorized cached-content behavior only under a defined ownership policy. Existing TabRoutesForRoleTest explicitly pins null engineer fallback and must be revised with rationale, not blindly retained. Do not infer engineer access or offer privileged roles from a missing value.

### 2. Signup's Sign in link can do nothing when entered directly from Welcome

**Source-verified:** Welcome pushes sign-up directly (AuthNavGraph:30). Signup's Sign in callback only calls `popBackStack(AUTH_SIGN_IN, false)` (45–46); that entry is absent on Welcome → Sign up. SignUpScreen:209 wires the link to that callback.

**Next:** navigation regression for both Welcome → Sign up → Sign in and Sign in → Sign up → Sign in. Small fix should navigate to Sign in when popBackStack returns false, preserving expected Back behavior and avoiding duplicate sign-in entries. This is a bounded, reversible early auth fix after failing regression is captured.

### 3. Repeat-booking language promises a chosen engineer that creation does not carry

**Source-verified:** completed-job CTA says “Book this engineer again” (RepairJobDetailScreen:2202); request header resource says “Booking %1$s” ([strings.xml:256](https://github.com/ganeshnaik166/equipseva-android/blob/05b73b522181145b1fabf3e4a2ae4d79096dd2b2/app/src/main/res/values/strings.xml#L256)). Yet `RepairJobDraft` has no engineer parameter ([Draft schema](https://github.com/ganeshnaik166/equipseva-android/blob/05b73b522181145b1fabf3e4a2ae4d79096dd2b2/app/src/main/kotlin/com/equipseva/app/core/data/repair/RepairJobRepository.kt#L104)); create inserts only the built draft payload ([Repository create](https://github.com/ganeshnaik166/equipseva-android/blob/05b73b522181145b1fabf3e4a2ae4d79096dd2b2/app/src/main/kotlin/com/equipseva/app/core/data/repair/SupabaseRepairJobRepository.kt#L230)). The prefilled engineer only hydrates the header. We did not inspect every backend trigger; an ID absent from the request cannot express this particular selected engineer to them.

**Next:** pin route-to-payload regression for a completed-job repeat entry; assert the actual submitted semantics. Small immediate correction is truthful copy and explicit review stating a marketplace request, with no guarantee of assignment. A true direct-engineer request requires a separately accepted backend eligibility/invitation contract. Do not “fix” this by merely passing engineerId from the public profile: that profile's existing generic label is intentionally accurate.

### 4. Engineer eligibility failure looks like missing KYC, and Jobs entry recovery differs

**Source-verified:** hub repository failure maps to `NotEngineer` (EngineerJobsHubScreen:106), same class as missing row, and renders a KYC onboarding CTA (188–200). A verified engineer with a network failure can therefore be told to become verified. Meanwhile Jobs tab prevents entering that hub with a snackbar, but Home enters its recovery hero. The hub still hides action tiles until verified; no KYC authorization bypass was established.

**Next:** deferred/failing repository regression distinguishes initial Loading, verified, missing engineer, pending, rejected and fetch Error. Render retry for Error without changing identity/KYC status. Then reuse one policy for Jobs/Home entry, keeping server bid checks intact. Include verifying no available-job action is exposed on unresolved/error status and return-from-KYC refresh behavior.

### 5. Failed payout-readiness query is treated as completed onboarding

**Source-verified:** profile repository catches payout RPC failure into null (SupabaseProfileRepository:49–53); Profile completion returns `hasEngineerPayoutComplete != false` (79). Thus an engineer with base fields but unverified payout readiness passes the global onboarding predicate. Session may also use sticky cached completion while fetching (SessionViewModel:162–165). This proves an app readiness ambiguity, not a payment/security exploit.

**Next:** regression uses an engineer with base fields plus payout query failure/null/false/true and cached completion. Introduce explicit Checking/Error versus Complete; protect previously authorized navigation and drafts while retrying. Keep current payment/backend enforcement. Progressive readiness is a product policy proposal, not permission to weaken the existing payout prerequisite.

## Preparation handoff

Recommended implementation order: the small sign-up link regression/fix; role/session resolution and failure states; truthful repeat-request review; unified Jobs eligibility/error recovery; explicit payout-readiness state. Root should choose the next bounded slice after current backend verification, then run appropriate Android checks and independent QA/critic. No tests were added or executed by this inventory task.

Prototype commitments may now use accurate current routes: direct hospital Request service is a deliberate new Home action; engineer Jobs starts as a verified hub; unknown role needs a workspace state; “same engineer” is not currently guaranteed. Keep new screens synthetic until required role policies, direct-booking semantics, provider behavior, accessible layouts and representative user tasks are validated. The broader M2a/M2b and ≥9.5 milestone gates remain open.
