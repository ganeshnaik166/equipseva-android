## Slice 2 — P2.2 client foundation in `core/data/location` (`23cc3ac5` + `22d343ac`)

Why: PRODUCT_PLAN §6 / delivery-ledger row P2.2 asked for (a) the bundled catalog's contradictory comments to be reconciled, (b) official stable codes plus a catalog version instead of bare names, and (c) legacy free-text values to resolve through explicit alias history — never substring guesses — and to surface as "needs confirmation" when anything is inferred.

What was found: `IndiaLocations.kt`'s header said coverage was "intentionally narrow" (Telangana plus a sample; other states fall back to free text) while the lists in the same file carry a district list for **every** State/UT (from 1 for Chandigarh/Lakshadweep to 75 for Uttar Pradesh, 764 in total) and mandals for 14 Telangana districts (257 mandals). The old `canonicalState` used a bare substring step, so "Goalpara" (an Assam district) resolved to the state Goa. The snapshot is uneven across States (Chhattisgarh has its 2022 districts, Assam lacks Bajali 2021 and Tamulpur 2022) and its transcription date is not recorded.

Files:

- `IndiaLocations.kt` — header rewritten to the measured truth; `CATALOG_VERSION = "bundled-names-v1"` (deliberately no claimed source year); `KNOWN_MISSING` map of districts known to be absent (Bichom, Keyi Panyor; Bajali, Tamulpur; Vav-Tharad; Changthang, Drass, Nubra, Sham, Zanskar; Maihar, Mauganj, Pandhurna; Meluri), pinned by a test so adding one forces the list and header to move; `canonicalState(raw, allowEmbedded = true)` resolves exact → normalized → explicit alias → whole-word embedded phrase on normalized text (one lazily precompiled pattern per State, rightmost embedded name wins; skipped with `allowEmbedded = false`); new `canonicalDistrict(state, raw, allowEmbedded = false)` — strict by default, with an opt-in whole-word step for Geocoder prefill where the longest embedded district wins. District lists themselves are unchanged (stored profile/engineer rows reference these spellings).
- `IndiaStateCodes.kt` (new) — LGD State/UT codes for all 36 entries (Census-2011 numbering; 36 Telangana, 37 Ladakh, 38 the merged Dadra and Nagar Haveli and Daman and Diu; retired 25/26 absent), `lgdCode()`, `stateForCode()`, `isUnionTerritory()` — strict by default — and a `SOURCE` provenance string. **District codes are not bundled** — they arrive with the reviewed LGD import and must not be invented.
- `IndiaRegionAliases.kt` (new, `internal`) — `normalize()` and the State/UT and State-scoped district alias tables (Orissa, Pondicherry, Uttaranchal, NCT of Delhi, Daman and Diu; Bangalore → Bengaluru Urban, Ranga Reddy → Rangareddy, Allahabad → Prayagraj, Maharashtra's Aurangabad → Chhatrapati Sambhaji Nagar while Bihar's Aurangabad stays, …). Two reverse aliases bridge current official names onto the older spellings the list still carries (Narmadapuram → Hoshangabad, Ahilyanagar → Ahmednagar). Deliberately absent: ambiguous city names (Bombay, Delhi, Burdwan, Secunderabad), "New Delhi" and "Dadra and Nagar Haveli" as State aliases (both are live districts). A test proves every alias targets a real catalog name, is stored normalized, shadows nothing, and that no State alias equals a district name.
- `LegacyCityParse.kt` (new) — `parseLegacyCity(raw, knownState = null)` reads legacy free-text location strings into canonical names. Where they come from (checked against the writers): `engineers.city` is written by KYC as `serviceAddress ?: serviceDistrict` — a "My location" line "line1, line2, landmark, city, district, state, pincode" or a bare district, with the State/UT in the separate `engineers.state` column (pass it as `knownState`) — plus the one-day `compose()` era "Mandal, District, State" and hand-typed "District, State" / "…, State, India". Reading order: the rightmost token that strictly resolves as a State/UT is the State (tail = remnants such as a pincode or "India"); among the tokens before it the rightmost district of that State is the district; the token immediately before that may be a Telangana mandal. Without any State, only a lone last token that is a nationally unique district may infer one, flagged. `needsConfirmation` means the region provenance is uncertain: inferred State, text/column disagreement (both reported in `stateCandidates`), an ambiguous lone district (`stateCandidates` lists the homes; the parser picks none), or text present but no district placed. Address remnants beside a resolved district stay visible in `unresolved` without forcing confirmation. Blank input is `EMPTY`, distinct from unresolved.

No UI, schema, RPC or caller changed. `KycViewModel` still carries its own ad-hoc split of `engineers.city` and a contains-both-ways Geocoder district match; migrating those call sites to `parseLegacyCity(raw, knownState = engineer.state)` / `canonicalDistrict(..., allowEmbedded = true)` is the natural next slice for whoever owns the KYC files (that file is heavily touched on the Codex candidate, so it was left alone here).

## Slice 3 — KYC prefill adoption of the catalog parser (`6492070e`)

Why: the two slices above changed no caller, so nothing reached users beyond the Geocoder state prefill. KYC step 1 pre-selects the State/UT and district dropdowns from the engineer row; it split `engineers.city` on commas and accepted the last part only when it was an exact catalog State, and it matched Geocoder labels with contains-both-ways string tests (a label such as "Nagar" could pre-select Ahmednagar).

What changed (only the two regions recorded in CURRENT_STATE; both lie outside every hunk the Codex candidate touches in `KycViewModel.kt`):

- `hydrate()`: `parseLegacyCity(engineer.city, knownState = engineer.state)` reads the real row shapes. Prefill is limited to what was stated explicitly: `parsedState` only when the State was not inferred and no candidates exist; `parsedDistrict` only when `needsConfirmation` is false. An inferred State (lone unique district), a text-vs-column conflict or an uncertain district stays blank for the engineer to pick — a guess never becomes the persisted service area. Profile fallbacks go through strict `canonicalState` / `canonicalDistrict` (also rescues "Orissa"-style legacy spellings).
- `onServiceCoordsChange()`: `canonicalState(resolved.state)` and `canonicalDistrict(state, resolved.district, allowEmbedded = true)` replace the substring tests.
- Location round-3 nits in the same commit: `LegacyCityParse.stateInferred`; an unrecognised token after the State token also makes the district a suggestion; spaced pincode counts as a remnant; "Distt" label stripped; explicit text with an unusable State column asks.

Tests: `KycViewModelTest` +4 (legacy alias city string → Telangana/Rangareddy; "My location" line with the State column keeps K.V.Rangareddy over the locality token Hyderabad; a lone "Hyderabad" prefills nothing and an unreadable district slot prefills the State only; a real `LocationFetcher.Resolved` payload with "Rangareddy District" / "Telangana State" canonicalises), `LegacyCityParseTest` +3, `IndiaRegionAliasesTest` +1 assertion.

User-visible effect (active market): rows such as "Ranga Reddy, Telangana" or "…, Hyderabad, K.V.Rangareddy, Telangana, 500032" now pre-select Rangareddy instead of nothing or Hyderabad; unknown labels leave the district for the engineer to pick. No UI, schema or RPC change; the persisted write still happens only on Save with the values the engineer sees.
