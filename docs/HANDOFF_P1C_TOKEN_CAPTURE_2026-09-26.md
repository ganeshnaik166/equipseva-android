## Owned change

`SignOutCleanup` captures one exact `LocalSessionOwnership.Ticket` before suspension, fences only that login's draft lease synchronously, captures its cached installation token with the same ticket, then awaits draft disk clear. The remote revoke attempt remains last. `RequestServiceDraftStore` validates the ticket under the ownership monitor before the synchronous fence and again inside DataStore's admitted edit before deleting the matching owner/session envelope. A stale A cannot fence B, erase B's draft, or erase a new A login's identical persisted envelope after an observed A→B→A. `DeviceTokenRegistrar.captureRevocation(ticket)` validates before and after its suspending DAO read and derives the revocation owner from the ticket, never live B. Cancellation is checked before/after best-effort cleanup and on token read/revoke error and completion paths. The old no-argument registrar and draft convenience methods remain for their existing callers/tests; sign-out no longer uses them.

Production ownership: `core/auth/SignOutCleanup.kt`, `core/data/repair/RequestServiceDraftStore.kt`, `core/push/DeviceTokenRegistrar.kt`. ## Mandatory boundaries and next step

The repository's `supabase/migrations/20260428320000_security_revoke_delete_grants.sql` revokes authenticated/anon `DELETE` on `public.device_tokens`. The Android registrar still issues client DELETE before registration upsert and for sign-out. If that grant state is deployed, the first denied DELETE skips registration upsert inside `runCatching`, and sign-out's attempted DELETE cannot remove A's row. **No live database grant was queried**; this is a repository-contract finding, not a claimed production 42501 observation. A secure fix needs a separate server/client/sender milestone with atomic revisioned claims and narrow release RPCs, not re-granting table DELETE. Read the [P1d gap](helper-reviews/codex-20260926/p1d-remote-token-gap.md), [schema inventory](helper-reviews/codex-20260926/p1d-schema-inventory.md), and [independent security critique](helper-reviews/codex-20260926/p1d-contract-critic.md) before implementing it. Same-user new-session delayed release, sender token-only invalid-row reap, background notification text, and offline logout must be covered there.

The P1c local guarantee does not cover the later global router/photo/preferences/realtime wipes, producers/readers, final SDK logout, S3 recovery, or guaranteed remote token removal. The next safe security work is P1d-0 sender payload/privacy and precise FCM error classification, with source-contract tests first; obtain an actual read-only/disposable `device_tokens` schema before implementing P1d-1 claim/release SQL. Keep the broad candidate off `main` while those gates and the push server contract remain open. Publish safe continuity docs separately; preserve other worktrees and the shared Gradle reservation.
