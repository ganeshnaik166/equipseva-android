## Source contract and resulting behavior

The sender still re-fetches the notification by webhook record ID and selects recipient tokens by the fetched `notif.user_id`. The outgoing FCM notification now always says **EquipSeva / You have a new notification.** Raw inbox title/body and arbitrary `notifications.data` keys never reach the FCM request. The data map contains the fetched recipient `user_id`, fetched `notification_id`, one of Android's 34 recognised `kind` values, its one matching validated route ID when present, and a constrained `channel`/`category`. An unknown kind or malformed route ID opens the app without a detailed route; the authenticated inbox remains available. Android foreground/background tap handlers use `kind`, the route ID and `user_id`; their destination fetch still uses current authenticated access. Android code was inspected, not changed or run on device.

FCM HTTP 404 is counted as `UNREGISTERED` only for a structured Firebase FcmError detail with `errorCode=UNREGISTERED`. A generic project/resource 404, a text substring, `INVALID_ARGUMENT`, 429 and 5xx are not token-invalid evidence. The sender no longer deletes `device_tokens` by token: a delayed invalid result could erase a newer account's claim. Its response reports `reaped: 0`; aggregate logs count invalid results but contain no token suffix or notification ID. OAuth and database error logs no longer include raw error bodies. Fresh valid sends remain possible; one thrown send no longer discards successful sibling accounting.

## Limits and next actions

1. P1d-0 does **not** make a token belong to exactly one current user. The tracked authenticated `device_tokens` DELETE revoke still conflicts with Android's DELETE-before-upsert and logout calls; actual deployed grants/table keys remain unverified. No SQL change should be inferred from sender-only tests.
2. Disabling automatic reaping leaves invalid rows, which can occupy the sender's ten most recently updated token slots and increase FCM calls. Watch aggregate `unregistered_count` and failed counts; build a revision-safe claim/reap contract after a disposable or authorised read-only table snapshot. Do not restore broad client DELETE.
3. A push already selected or sent before an A-to-B transfer can still reach the physical device. Generic visible text limits tray exposure, but the minimal route IDs/kind and recipient UUID remain in FCM data. Android's recipient guard and authenticated destination fetch require an actual foreground/background shared-device pilot.
4. A transport exception produces a non-2xx sender response like the old rejected `Promise.all` path. Supabase webhook replay policy is **unverified**; a replay, if configured, can duplicate successful sibling pushes. Completed FCM 429/5xx responses retain the old HTTP-200 acknowledgement behavior. Durable per-token delivery and retry need a separate design; no exactly-once claim is made.
5. Local alias resolution passes two Deno CLI versions, but Supabase CLI/edge bundle compatibility on this laptop is **unverified**; a deployment dry run is a separate gate. Independent critic/QA and device/provider verification must precede sender deployment. P1d-1 requires actual `device_tokens` schema/RLS/grants, versioned claim/release/reap, old-client compatibility and a two-session race suite.
