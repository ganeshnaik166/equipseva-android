## Problem and bounded change

Round3828 revoked client EXECUTE on nine present service-only money functions. It did not change future function defaults. Read-only production catalog inspection on 27 September found `postgres/public` and `supabase_admin/public` default function EXECUTE grants to `anon`, `authenticated`, `postgres`, and `service_role`, and no global function ACL override for either creator role. PostgreSQL's built-in global function default includes `PUBLIC` EXECUTE. All 19,363 current `public` functions are postgres-owned (532 effectively executable by anon, 19,269 by authenticated, all by service_role); these aggregate permissions do not classify the functions as vulnerabilities. The nine round3828 exact signatures remain present and effectively executable by 0/9 anon, 0/9 authenticated, 9/9 service_role. `postgres` is not a member of provider superuser `supabase_admin`; the migration deliberately does not touch its default ACL.

Round3829 first revokes global `PUBLIC` EXECUTE on **future postgres-created functions**, then removes the separate `anon` and `authenticated` default grants for future postgres-created `public` functions. A schema-only `REVOKE ... FROM PUBLIC` cannot undo the global built-in grant. The public-schema `service_role` default stays, so existing service-role creation patterns remain possible. The migration is transactional; it snapshots all existing public-function ACLs and the `supabase_admin/public` function-default ACL, then checks those are unchanged, the global override exists without PUBLIC, direct client defaults are gone, and public-schema service-role default remains. Existing functions' ACLs are not rewritten by this migration.

This global change also makes future postgres-created helpers in `extensions` private until explicitly granted. The production catalog has 49 existing postgres-owned `extensions` functions; their current ACLs are unaffected. Future Supabase/provider or application code that creates such functions needs review and explicit grants. `supabase_admin` can still create public functions using its separate permissive defaults, so this is a postgres-creator boundary, not a complete project-wide default-policy closure.

These are representative paths, not a complete caller inventory or a deployed old-client test.

Every future new client RPC must grant exact-signature EXECUTE to the intended role in its defining migration. `CREATE OR REPLACE` retains a function's existing ACL; DROP+CREATE loses it, so the migration must replay the intended grants inside the same transaction. `service_role` defaults remain for new public functions, but a future extension-schema helper needed by that role must grant it explicitly. Server body authorization, tenant checks and `auth.uid()` remain required in addition to EXECUTE.
