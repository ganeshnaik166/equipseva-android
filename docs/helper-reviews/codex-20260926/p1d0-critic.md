## Source-backed findings

1. **Visible and data privacy:** `index.ts:245-267` re-fetches the notification by webhook ID under service role and selects tokens for the fetched `notif.user_id`, rather than trusting `record.user_id`. `push_contract.ts:60-101` constructs fixed visible text (`EquipSeva` / `You have a new notification.`), derives recipient and notification IDs from the fetched row, copies only a recognized kind and its one validated route ID, and sets a constrained category/channel. It never forwards stored title/body or arbitrary `notifications.data`. `push_contract.test.mjs` asserts spoofed owner/kind/ID, private text, malformed/encoded route IDs, matching job/AMC/chat IDs and exact fake-FCM wire JSON. The regexes match `NotificationDeepLink.kt`'s UUID and `RPR-1..8 digits` route forms; 34 Android kind constants are checked by a source-parity test.
2. **Android reception caveat:** `EquipSevaMessagingService.kt` uses the new generic FCM notification text when foreground and carries `user_id` on its PendingIntent. For a background notification-plus-data message, Android's system tray can post without the service; generic text is therefore necessary. `DeepLinkRouter.kt:103-136,267-272` applies an external route allow-list and checks the recipient ID at login delivery. This was source inspection, not a physical-device test; data still includes A's UUID, kind and validated entity ID on a device later used by B. The current router and target RLS must be verified in a real A→B foreground/background pilot before rollout.
3. **FCM error boundary:** `push_contract.ts:105-118` marks unregistered only when HTTP 404 carries a structured Firebase FcmError detail with `errorCode=UNREGISTERED`. Generic 404, text substrings, `INVALID_ARGUMENT`, 429, 5xx and malformed JSON do not become token-invalid evidence. This follows the [official FCM error contract](https://firebase.google.com/docs/cloud-messaging/error-codes). Since reaping is disabled, even a true invalid classification only increments an aggregate counter.
4. **No unsafe reap/log exposure:** `index.ts:286-319` has no `device_tokens` DELETE and returns `reaped: 0`. Logging is aggregate, without token suffixes, notification IDs, raw OAuth/DB errors, title or body. `sendBatch` catches each token's thrown send, retains successful sibling counts, and reports a transport failure. A delayed FCM result cannot remove a newer user's token row through this sender.
5. **Webhook replay remains an integration gate:** one transport exception after other tokens succeeded yields 502. If the webhook dispatcher retries, successful siblings may get duplicates. Completed FCM 429/5xx responses still get HTTP 200, preserving the previous acknowledgement contract. The tracked SQL trigger uses asynchronous `net.http_post`; deployed retry/replay policy and delivery ledger were not verified. Do not claim exactly-once or guaranteed retry.
