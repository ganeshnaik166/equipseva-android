## Code finding

`SignOutCleanup` checks cancellation and captures one `LocalSessionOwnership.Ticket` before its first suspension. `RequestServiceDraftStore.fenceForSignOut` checks that exact ticket while holding the ownership monitor and retires only the matching draft lease synchronously. `DeviceTokenRegistrar.captureRevocation(ticket)` checks the ticket before and after the suspending local token DAO read, then derives the owner from the captured ticket. A direct B replacement, same-owner new session, observed A→B→A, null ticket, failed read, or cancelled caller cannot publish B's token as A's revocation pair. The later `clearFencedForSignOut` checks the ticket inside the admitted DataStore edit and preserves B's committed draft. `bestEffort`, token capture and revoke recheck cancellation around noncooperative dependencies, so cancellation does not silently continue into later global wipes.

The older no-argument `captureRevocation()` and `revoke()` convenience paths remain weaker across suspension. I found no production call site using them; sign-out now calls the ticketed overload. A missing exact ticket intentionally skips ticketed draft deletion and token capture. Unsupported/missing session claims and unobserved identical identity boundaries therefore remain limitations, not evidence of whole-app cleanup.
