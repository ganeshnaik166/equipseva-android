## Required release limits and follow-up

1. A push selected or sent to A before an A→B device transfer can still arrive on B's physical device. The generic text prevents sensitive tray content, including the system-posted background path, but FCM `data` still has A's UUID, kind and validated route ID. Foreground `EquipSevaMessagingService.kt:48-141` posts without checking the current account. Background notification-plus-data bypasses that service and reaches `DeepLinkRouter.kt:128-137` on tap. The router has a recipient check at `:268-271` and login-generation handling, but wholly unobserved identity boundaries are not proven safe. Run an actual foreground/background A→B and sign-out/sign-in shared-device pilot before deployment; do not claim account isolation from this slice.
2. `index.ts:259-270` still selects ten most recently updated device tokens. With reaping intentionally disabled, invalid rows can eventually consume those ten slots and suppress a fresh token. P1d-1 must verify real schema/grants and introduce a revision-safe claim/release/reap contract; do not restore broad client DELETE. The actual deployed grants, token ownership and notification ID schema were not queried in this QA.
3. `index.ts:306-319` returns 502 after one thrown send even when siblings succeeded. Any configured webhook replay could duplicate those sends; a per-token ledger is needed for exactly-once or selective retry. Provider retry behavior is unverified.
4. `deno.json` has a function-local pinned import map and no lockfile. The two local Deno CLI checks do not prove Supabase's edge bundler, hosted runtime or FCM delivery. No Supabase CLI bundle/deploy, live FCM, physical device, or Android test/build was run for this sender-only review. The handoff accurately marks these limits and does not overclaim A→B isolation. The Deno 2.9.7 archive matched a published SHA-256; 1.46.3 provenance was official release URL/API size only, as corrected in handoff HEAD `e18f3ca2`.
