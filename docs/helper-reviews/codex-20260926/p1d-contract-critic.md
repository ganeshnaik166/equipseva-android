## Confirmed boundary

`20260428320000_security_revoke_delete_grants.sql:1-15,29` revokes authenticated/anon `device_tokens` DELETE. `DeviceTokenRegistrar.kt:70-98` still places DELETE before upsert inside one swallowed `runCatching`; `:167-184` swallows ordinary logout DELETE errors. If the tracked grant is deployed, registration/release can fail. The live grant was not queried. ## Additional risks to design and test

1. **Two registration callbacks can reorder.** `SessionViewModel.kt:328-340` calls `refresh()` on login while `EquipSevaMessagingService.kt:39-45` calls `register(token)` on rotation. If a new claim RPC issues a fresh revision on every call, two responses can arrive out of order. A late older response can overwrite the locally persisted newest revision; a subsequent release then misses the live claim. The same can happen across A/B or a retry after a lost response. Bind both entry points and all local claim writes to an exact login ticket plus token and request generation, or make claim retries idempotent and reconcile the current server revision. Test A/B, same-user re-login, simultaneous refresh/onNewToken, lost response, restart and cancellation. `DeviceTokenRegistrar.kt:70,92-96` currently reads live auth around suspension; those checks do not provide this ticketed response ownership.
2. **An authenticated caller must not transfer an arbitrary token merely by naming it.** The proposed one-token claim would make the caller the destination for future messages and evict the prior owner. A stolen FCM token could cause denial of service or cross-user delivery. Define token possession proof (for example, a short-lived FCM challenge redeemable by the installed app), abuse limits, replay protection and audit events before allowing cross-owner transfer. App/device attestation may reduce abuse but does not establish that the caller controls a particular token by itself. Also reject disabled/deleted accounts where product policy requires it. Avoid claiming rooted or cloned clients can be made impossible.
3. **Sender data is not recipient-safe.** `send_push_notification/index.ts:187-196,349-359` forwards `notif.title`, `notif.body` and arbitrary `notif.data`; it only fills `kind`/`notification_id` when missing, and never forces `user_id = notif.user_id`. `EquipSevaMessagingService.kt:79-100,141` uses `data.user_id` only for tap routing and posts foreground content without a recipient check. Background notification payloads are shown by Android/FCM before that receiver path. A generic visible title/body alone is insufficient if arbitrary data still contains job/chat/identity details. Test an adversarial `notif.data` with spoofed `user_id`, title/body and unexpected PII keys; enforce an allow-listed safe payload and server-derived recipient before sending. Preserve required routing fields deliberately, and require authenticated fetch on tap. An already sent push remains in flight after transfer.
4. **Dead-token classification can erase a healthy newer claim.** `send_push_notification/index.ts:212-225` treats any FCM HTTP 404 as `UNREGISTERED`, including a project/resource 404, then `:362-365` deletes by token alone. Tests should distinguish a structured FCM token-unregistered response from generic 404/other failures; stale results must compare row ID and claim revision (or equivalent generation) within the server mutation. The sender fetches only `id, token` at `:324-329`, so it currently lacks a generation to compare. Do not add a version-dependent delete until the actual table schema is known.
5. **Offline and moved-auth logout remain separate.** `SignOutCleanup.kt:75-88,132` captures local A before disk work but performs remote release last, when a replacement B SDK session could already be active. A narrowly authenticated release should reject an A claim sent with B's JWT. That is safe but leaves A's row until B atomically claims the token or expiry/reconciliation removes it. The client must record a failed release/retry state without calling logout incomplete; sender payload minimization protects the residual interval. A successful client HTTP mock is not proof of deployed grants or FCM behavior.

## Smallest safe test-first slice

**P1d-0: sender privacy and classification, independent of unknown SQL schema.** First extract pure payload construction/error classification helpers, preserving the existing route contract after an explicit data-field inventory. Write failing Deno tests for sensitive notification title/body and extra `data` fields, spoofed recipient ID, valid routing fields, FCM generic 404 versus token-specific `UNREGISTERED`, and an in-flight A-to-B device switch. Then make visible content generic, allow-list data, force recipient from the fetched notification, and classify dead tokens narrowly. Do not change `device_tokens` DDL, grants, client registration/release or token reaping in this first slice; the existing token-only reap should be separately disabled or fenced once row identity/revision is known. Validate the Deno tests and sender function checks, then an authorized foreground/background device pilot before claiming delivery/privacy acceptance. A sender-only score must not imply server claim/release or S1 completion.

Before **P1d-1 claim/release**, obtain a disposable baseline or authorized read-only snapshot of actual table columns, constraints, RLS, grants, deployed migration/function versions and duplicate-token counts. Write native PostgreSQL two-session RED tests for competing claims/releases and privilege denial before migration code. Keep direct authenticated DELETE revoked, derive caller identity from `auth.uid()`, version each claim, use exact owner+revision release, and decide old-client rollout/rollback before altering privilege or delivery behavior. The current notes' proposed RPC shape is a hypothesis until this evidence exists.
