# P1d candidate — remote device-token ownership gap

Read-only investigation, 26 September 2026. This is a later server/client slice, separate from P1c's bounded local ticket, draft fence, and token capture. No live database, FCM account, credentials, Gradle, or provider call was used.

## Repository evidence and present risk

- `supabase/migrations/20260428320000_security_revoke_delete_grants.sql:1-15,29` deliberately revokes `DELETE` on `public.device_tokens` from `authenticated` and `anon`. The tracked migrations do not contain a token claim/unregister RPC or a later direct DELETE grant. `docs/helper-reviews/codex-20260919/push-navigation-independent-review.md:34-38` records a wider search of 3,378 migrations, including dynamic grants. The table's original DDL, keys, and policies are not in the tracked migrations inspected here. **The live database was not queried**; a deployed grant/constraint difference remains possible. If the tracked revocation applies there, the client DELETEs are denied, likely with SQLSTATE `42501`.
- `app/src/main/kotlin/com/equipseva/app/core/push/DeviceTokenRegistrar.kt:66-92` writes the installation token locally, then issues authenticated DELETE by token before remote upsert inside one `runCatching`. A denied DELETE skips that upsert and hides the failure. `:148-164` also attempts authenticated DELETE by captured `(user_id, token)` during logout and ignores ordinary errors. P1c makes the captured pair stable; it cannot grant the missing server permission or prove that a remote row was removed.
- `supabase/migrations/20260424120000_delete_my_account.sql:32-62` has a SECURITY DEFINER account-erasure RPC that deletes all the caller's tokens. It is not a logout/token-transfer API.
- `supabase/functions/send_push_notification/index.ts:324-329,358-365` selects each recipient's rows by `user_id`, sends to every selected token, then deletes FCM-invalid rows by **token alone**. It shows no cross-owner dedupe or claim revision check. `:349-356` does not force `notif.user_id` into the data payload, while `:187-196` includes a notification title/body. The Android receiver reads a recipient hint only for tap routing at `EquipSevaMessagingService.kt:95-100`; it does not reject a mismatched push before posting at `:141`. [Firebase's Android receive guide](https://firebase.google.com/docs/cloud-messaging/android/receive-messages) confirms that background notification-plus-data messages appear in the system tray without `onMessageReceived`, so a receiver-only filter would not protect that path.
- The remote row is currently identified for revoke by user and token, not a registration version (`DeviceTokenRegistrar.kt:42,114,153-156`). If direct DELETE were restored, an old A logout could delete a fresh **same-user** login's registration of the same physical token. Where the versioned revoked grant is applied, it prevents that DELETE but also prevents legitimate logout. The server sender's token-only dead-row reap has a similar late-delete race against a fresh claim.

## Least-privilege contract to design and verify

Keep authenticated/anon table DELETE denied. Introduce narrow SECURITY DEFINER `claim_device_token` and `release_device_token` RPCs, with a fixed empty `search_path`, schema-qualified references, explicit non-null `auth.uid()` and verified JWT session checks, bounded token input, no caller-supplied owner ID, no raw-token logging or echo, `REVOKE EXECUTE FROM PUBLIC, anon`, and `GRANT EXECUTE TO authenticated` only. Review the function owner's privileges and prevent unrelated table access.

`claim` should atomically establish **one current owner per FCM token**, return a new opaque claim UUID/revision for every successful registration, and serialize competing claims with a unique token constraint or an equivalent database lock. `release` should compare the authenticated owner and exact captured claim revision (and token/row identity) before deleting. A delayed A release then cannot remove B's claim or a new same-user A claim. The Android client must persist the server claim revision with its originating login, capture it before sign-out suspension, replace its DELETE-then-upsert with the atomic claim RPC, and report/retry 401/42501/network failures without blocking local logout or discarding the installation token. A token value is a bearer-like input: cross-owner claim transfer needs a documented possession/attestation threat model, abuse limits, and audit evidence rather than unrestricted arbitrary-token deletion.

The sender must select current claims and compare the fetched claim revision when reaping an FCM-invalid token; deleting all rows by token is unsafe after a concurrent re-claim. For shared-device privacy, make notification content generic or move to data-only delivery with a verified recipient check and an authenticated fetch after receipt. A push selected or already sent before a claim transfer remains an in-flight limitation. Offline sign-out cannot instantly revoke a server row; use retry/claim transfer, bounded expiry, and non-sensitive payloads as part of the recovery policy.

## Migration and verification prerequisites

1. Inspect a disposable database built from the relevant baseline, or an authorized read-only schema snapshot, for actual `device_tokens` columns, unique keys, RLS and grants. Decide how legacy duplicate token rows are quarantined before imposing one-token ownership; do not infer a unique key from this repository. Stage Android Room persistence for claim revision and an old-client rollout before revoking any direct INSERT/UPDATE path. Keep direct client DELETE denied; a safe rollback must not re-enable stale cross-account rows.
2. Use disposable SQL tests to prove direct authenticated DELETE remains denied; only authenticated callers can execute the RPCs; spoofed owner, anon, malformed token and wrong claim revision fail; A→B, A→new A session, same-token refresh, concurrent claim/release and retry preserve the newest claim. A native PostgreSQL two-session test should exercise the transaction ordering; a single-connection mock cannot prove it.
3. Add Android synthetic HTTP tests for claim/release success, 401/42501/timeout, cancellation, offline retry and persisted revision recovery. Add sender tests for claim-checked lookup/reap and recipient-safe payload. Finish with an authorized provider/device pilot for foreground and background delivery; synthetic HTTP 204 responses do not establish deployed grants or FCM behavior.
