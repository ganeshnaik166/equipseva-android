The actual deployed schema, role grants, RLS policies, existing duplicate token rows, sender deployment revision, webhook wiring, and provider state remain **unknown without an authorized read-only snapshot or disposable database**. Do not infer a live 42501 or a unique-key violation from source alone.

## Minimal test-first rollout order

1. **Discover and preserve old clients.** Obtain an authorized read-only schema/grant/policy/duplicate-count snapshot, or reconstruct the relevant baseline in a disposable Supabase/PostgreSQL environment. Record current deployed migrations and sender version. Decide how old Android clients that still call DELETE/upsert will behave during rollout; do not re-grant broad table DELETE.
2. **Write failing database and sender tests.** Verify authenticated/anon direct DELETE denial; unauthenticated and spoofed-owner claims denied; malformed/oversized token denied; exact user plus opaque claim revision required for release; A→B, A→new A login, retry and concurrent claim/release keep only the latest claim. Use two database sessions to prove serialization. Test sender's stale invalid-token result against a fresh claim, plus foreground/background recipient-safe payloads.
3. **Add server contract before Android switches.** Migrate legacy duplicate rows deliberately; add a unique/serialized current-token claim with an opaque revision. Narrow SECURITY DEFINER `claim_device_token`/`release_device_token` to `authenticated`, schema-qualified objects and a locked-down search path, deriving owner from `auth.uid()` rather than a caller-supplied user ID. Bound inputs, avoid raw token logs/echoes, and define a possession/abuse model for client-supplied FCM tokens. Keep direct DELETE denied. Version-check the sender's invalid-token reap and make sensitive visible content recipient-safe before transfer is relied on.
4. **Switch both Android registration paths and logout.** Persist the server claim revision with the originating login; use atomic claim for sign-in and `onNewToken`, and exact revision release for sign-out. Preserve the installation token through logout. Make 401/42501/offline failures observable with bounded retry, without blocking local logout or treating a failed release as success. Add synthetic cancellation, process-restart and A/B/same-user tests.
5. **Gate release on deployed evidence.** Exercise the disposable database race suite, then a controlled provider/device pilot for foreground, background and offline shared-device switches. Verify deployed grants/function ownership, claims, sender version and FCM behavior. Roll back by disabling the new call path or sender feature, not by restoring unrestricted client DELETE. A push already sent before transfer is an in-flight limit; account isolation also needs non-sensitive notification bodies and authenticated fetch after open.

This is a P1d plan, not an accepted schema migration or a production finding. P1c remains a narrower local capture/draft boundary.
