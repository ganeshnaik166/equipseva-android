# S1/A4: implementation boundary and next test-first slice

Reviewed against integration base `69034d84933c961e6f20c504da6f81158b9aed36` and the coordinator's working S2 diff on 2026-09-19. Read-only analysis: no production/test edits, Gradle, staging or commits for this subtask.

## Disposition

**S1 remains open. Keep all three reproduced failures and the passing ordinary-cleanup control in `SignOutCleanupLocalBoundaryRegressionTest`. The broad app candidate remains WIP; do not merge it to main or assign a passing A4/security score.**

Moving token capture ahead of draft persistence fixes only the first demonstrated race. Checking auth before `clearAll()` does not make the eventual mutation owned: Room/DataStore scheduling, mutex acquisition, WorkManager operations and realtime unsubscribe can all finish after another login has begun. A reorder-only patch is explicitly rejected as acceptance.

The three existing failures cover (1) capture of B after A's draft clear stalls, (2) B's new outbox row erased when that draft clear resumes, and (3) B's payment marker erased after A's outbox clear suspends. Existing mock-based ownership tests only establish ordering relative to the final network revoke; they do not establish ownership of the local writes. Keep their assertions and update the old ordering expectation transparently if a real API redesign changes the order.

## Verified realtime collision evidence

Inspected the **cached declared dependency** `io.github.jan-tennert.supabase:realtime-kt-android:3.6.0`, AAR hash directory `a80b5383ca02ef00bf6f8ae5839776d3b675e1db`. No dependency change or Gradle operation was performed. Extracted classes only into the external review output directory.

`RealtimeImpl.removeChannel(channel)` bytecode first awaits `channel.unsubscribe()` when subscribed (offset 129). After that suspension, it executes `_subscriptions.remove(channel.topic)` (offsets 160-173), not a compare-and-remove of the captured instance. `RealtimeImpl.channel(id,builder)` returns the object already stored under the topic (offsets 22-52), or installs a new object under that key. `addChannel` also writes by topic. Thus an A teardown can act on B's reused/replaced same-topic subscription. Existing `awaitClose` cleanup scopes have the same boundary; a snapshot in SignOutCleanup alone does not repair them.

Evidence: `outputs/quality-review-20260919/realtime-3.6.0-bytecode.txt`. This is source/bytecode confirmation of the unsafe primitive, not a claimed executed app regression test. Add a synthetic held-unsubscribe/reacquire test before implementation. Do not append a login suffix indiscriminately to typing broadcast topics: both conversation participants must still share the intended server topic. A lease manager serializing shared-topic acquire/remove is the safer architecture.

## Minimum next test-first slice

1. **Introduce a shared local session ownership ticket, without claiming full A4.** Capture user ID plus stable SDK session identity synchronously; include an observed generation/revision and a raw-current identity probe. `session_id` is an isolation key, not authorization. Token refresh within the same SDK session preserves the ticket; an observed logout, direct replacement, same-account new session or retirement invalidates old callbacks. Define behavior for unavailable session IDs rather than adopting future users. The draft store already has a useful implementation pattern but should not become the owner of unrelated resources.
2. **Implement cleanup deletion safety inside storage boundaries.** Start with real DataStore prefs/payment-store tests and a real Room outbox transaction test. Pass the captured ticket into cleanup-specific APIs; evaluate it inside the serialized transform/transaction. This is an implementable bounded slice and can prove that a late A cleanup does not erase committed B data. It does not yet solve all stale producers/readers. The token capture API must accept the already captured user ID; moving its current no-arg call alone still leaves a new suspension before the draft fence unless that fence is split/owned.
3. **Finish orchestration only after all invoked mutation owners are safe.** Add owned stash/cache operations, explicit scheduling disposition and realtime leases. Remove global asynchronous teardown only when its replacement is wired and tested. Route profile, payout, zombie and root-gate logout through the same owner. Capture before draft/Room suspension, but never let a stale caller invoke logout against a replacement SDK session.
4. **Then migrate stale producers and readers.** Persist owner metadata for outbox/payment/prefs state, stamp at the originating action before its async work, and read only the current owner's data. This is the wider A4/A12 work: a late callback entering an ownerless setter under B cannot be repaired by capturing B at setter entry. Ownerless legacy data needs an explicit migration/quarantine policy. Same-account re-login requires session/generation evidence, not just matching user IDs.

Suggested tests, in addition to retaining the three existing reds:

- Gate token-cache read before the draft fence, replace A with B, and prove neither B's draft lease nor B's remote token is targeted.
- Delay DataStore **before transform admission**, commit B's marker/prefs first, release A clear: B remains. Also delay A's disk commit after its transform, queue B's write behind it, release: B is committed afterward and remains. Include a same-ID replacement and repeated same payment ID with a newer revision.
- Use real Room: suspend cleanup before transaction admission while B enqueues; then reverse ordering with cleanup already holding the write transaction. B's row must survive either serialization order. Ensure ordinary A cleanup still deletes A work.
- Hold stash lock, replace account and write B bytes; old cleanup cannot delete B's exact file. Verify unique paths and stale enqueue orphan cleanup.
- Hold cache mutex/realtime unsubscribe/WorkManager cancellation, create B's replacement, then release A. B cache/channels/work remain, while ordinary A teardown completes.
- Hold the final SDK logout/import boundary: A→B and A→signed-out→A must not let A's old operation clear the replacement SDK session. Caller-level checks alone do not prove repository-level mutation ownership.
- Cancellation must propagate from every cleanup step and from all callers. Never delete, ignore or reclassify a failing target to produce acceptance; adapt fixtures to new APIs while preserving each safety assertion and ordinary positive control.

## Logout UX/recovery contract required

Logout is a transaction owned by the current login. During revocation the protected UI stays gated. A failed/cancelled cleanup cannot silently return the same A to Ready with retired draft/router leases and a revoked push registration.

Two explicit outcomes are acceptable: finish/retry local logout; or offer an owned recovery path that verifies the exact still-current SDK login, reloads its required state, re-registers its token and issues fresh routing/draft generations. That recovery must never revive old buffered links. Generic `refreshNow()` is not currently such a transaction. The money reviewer independently found this S3 edge: `clear()` intentionally blocks cached A, while gate cancellation recovery can return A to Ready without an auth boundary. Plain remote network failure is not enough to reproduce this because `SupabaseAuthRepository.signOut:241-261` attempts LOCAL fallback; cancellation or failed local removal are the relevant cases.

## Independent S2 judgment

The coordinator's S2 diff removes only the unconditional local token-cache clear from `DeviceTokenRegistrar.revoke`, retaining the captured `(user_id, token)` remote DELETE. **No introduced blocker found in this scoped source review.** The entity is installation-scoped (token/platform/time, no account); every observed login refreshes/registers independently of cache existence, and signed-out capture still returns null. Firebase retains its underlying token regardless of this Room row. Retention prevents A's late revoke from deleting B's cache, including when both use the same physical token.

The ordinary control was transparently changed from cache-deleted to cache-retained while preserving HTTP filter assertions; a new signed-out control checks no remote request and retained cache. That is a documented policy correction, not removal of the failing A/B target. This review did not run those tests and does not claim a green result or whole-push acceptance. Existing capture/register races, offline remote revocation failure, caller cancellation handling and server-side token ownership remain separate boundaries. `register()` still performs a live-auth-dependent token DELETE/upsert sequence; retaining the local installation cache does not claim to fix it.

No production/test change was made by this review. Existing failures remain intact.
