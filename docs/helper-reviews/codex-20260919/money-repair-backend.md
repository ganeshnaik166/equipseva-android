## Findings that need action

### M1 — P1: The repaired 5xx dispatch can downgrade an already completed payout

- Changed code: `supabase/functions/process-engineer-payouts/index.ts:527-535` calls the dispatch RPC with the now-valid `processing` status and `PROVIDER_5XX_RETRY` marker. Lines 232-236 reclaim this marker on a later run.
- Contract: the sole versioned definition of `record_engineer_payout_dispatch`, `supabase/migrations/20260713100000_round424_engineer_payouts_worker_rpcs.sql:149-155`, assigns `status = p_status` with only `WHERE id = p_payout_id`; it has no terminal-state or dispatch-attempt guard.
- Reproduction by source interleaving: a retry claims a row with a reference from a previous transfer; the delayed signed success webhook writes `processed`; then the in-flight retry receives a 5xx and records `processing/PROVIDER_5XX_RETRY`. The next worker invocation requeues and dispatches that completed payout again. The same success webhook cannot repair it because the current webhook RPC returns on its already-inserted dedup key (`20260721200000_round466_payout_reconciliation.sql:70-80`).
- Regression distinction: the RPC weakness already affects ordinary success/duplicate dispatches and the unguarded auth-error bulk requeue. This patch extends it to the repaired 5xx path: the old invalid `queued` argument raised 22023 before updating the row. Preserving the provider reference is good, but is not a monotonic-state guarantee.
- Consequence: a completed transfer can remain shown as processing/failed and be retried indefinitely. Stable transfer IDs reduce duplicate-provider-charge risk; they do **not** prevent the local ledger downgrade, and no new transfer ID should be generated as a repair.
- Minimal fix/test: make a versioned, drift-checked dispatch/claim operation monotonic with a captured attempt/lease and a result that distinguishes ignored terminal rows; also restrict auth-failure requeue to the owned current claim. Run a synthetic database barrier test: webhook-success before delayed 5xx record, then replay webhook, and assert `processed`, reference, UTR, and no subsequent pickup remain. Include reversed/failed, old attempt versus new attempt, and the success/duplicate paths. A worker-only pre-read leaves a race and is insufficient.

### M2 — P1: Cold-start recovery erases a paid-but-uncredited AMC payment's repair proof

- Changed recovery: `app/src/main/kotlin/com/equipseva/app/core/payments/PendingAmcPaymentsReconciler.kt:63-72,84-102`; a `paid` status clears the marker before considering the newly stored verify payload. The removal also deletes its signature (`PendingAmcPaymentsStore.kt:61-75`).
- Actual edge contract: `supabase/functions/verify-amc-payment/index.ts:284-297` marks the order `paid`, then separately invokes `apply_amc_pool_credit` at 316-325; a failure at that RPC returns 500. Its explicit repair path at 236-272 re-verifies an already-paid order with no credit ledger row.
- Reproduction: SDK success; status update succeeds; pool-credit RPC fails throughout all three foreground retries; restart. Status fetch says `paid`; the reconciler deletes both the marker and the only stored client payload without invoking the server's missing-ledger repair path. The hospital's contract/pool can stay uncredited while recovery claims completion.
- Classification: the server's non-atomic paid/credit split and the old status-only sweep predate this branch. The new persisted-proof recovery is incomplete and throws away its new repair capability in precisely the supported server partial-commit state.
- Minimal fix/test: for `paid` with stored proof, verify/confirm a credit ledger before deleting proof; keep it on failed confirmation. Keep refunded/failed terminal handling distinct and do not replay an unknown future state. Synthetic reconciler tests should cover paid+proof+missing-credit repaired, verification failure retains proof, already-paid+existing-credit idempotent success, and paid without proof. Prefer a future server atomic transition so status alone can eventually be trusted.

### M3 — P2: Typed 4xx classification now suppresses real transient AMC verification retries

- `AmcPaymentSheet.kt:331-341` treats every `EdgeFnHttpException` in 400..499 as deterministic; the wizard uses the same helper. `AmcRepository.kt:495-509` preserves HTTP status but discards structured failure `code`.
- The actual server contract is not that simple: `_shared/razorpay_server_verify.ts:85-105` returns `razorpay_fetch_failed` or `razorpay_503` on a provider connection failure/outage; `verify-amc-payment/index.ts:217-233` maps **all** those failures to HTTP 400. A concurrent paid transition also deliberately returns 409 with retry-or-check-status copy (308-312).
- Reproduction: after checkout success, mock the exact server envelope `{ok:false,code:"server_verify_failed",message:"payment did not match expected amount/order/status: razorpay_503"}` with status400. The new helper returns false, so the foreground flow makes one attempt and gives up, unlike the intended transient retry path. Existing tests use made-up direct502 and signature-mismatch400 cases and miss this real 400 shape.
- Minimal fix/test: distinguish transient provider-read failures from deterministic signature/amount/owner refusals using a structured contract. Prefer correcting the edge response to a retryable status for provider outages plus preserving machine codes in the repository; test the real edge error envelope through repository and checkout, retaining no-replay tests for actual deterministic refusals. Do not weaken all 4xx into blanket retries. A 409 needs status/credit reconciliation, not an assumption that nothing changed.

### M4 — P2: Whitespace still silently changes an agreed SLA

- `CreateAmcWizardScreen.kt:1338-1340` trims both strings in `canProceedSlaStep`; `submitAndPay` at 440-441 parses the **untrimmed** strings and defaults to 4/24 hours. Setters store raw text and `EsField` forwards it unchanged.
- Reproduction: paste emergency `" 2 "` and standard `" 8 "`, pass the SLA step, submit from Engineer step. The request contains 4 and 24 instead of 2 and 8.
- The integer-only change correctly refuses fractional hours, but does not establish its claimed invariant that the selected and transmitted values are equal.
- Minimal fix/test: share a parsed, validated whole-hours value between page gate and submit; reject invalid/restored state instead of silently defaulting. Use the real wizard ViewModel with captured `createContract` arguments for padded values and prove invalid state causes zero writes. A pure gate test alone cannot detect this mismatch.

### M5 — model-level residual, not a proven root-host regression: Hub retains another engineer's verification if its ViewModel is reused

- `features/engineer/EngineerJobsHubScreen.kt:89-109` collects sessions serially across a suspend fetch; its new failure handler preserves the previous `Verified/Pending/Rejected` state at 145-152 without recording the account that owned that evidence.
- Reproduction in a retained ViewModel: load A as Verified; emit SignedIn B directly; make B's fetch fail. B retains A's Verified tile presentation. The former failure branch reset to NotEngineer. Delayed A results and blocked sign-out observation are separate existing weaknesses of the serial collector.
- Minimal fix/test: own status/request by observed login identity/generation, retain known data only for a refresh belonging to the same login, reset immediately on account boundaries, and avoid suspending the full session collector on I/O. Test direct A→B failure, sign-out→same-A, late noncooperative result, duplicate email-only events and valid fresh retry. Coordinate with auth owner's root host guarantees before claiming app-level exploitability. This is a presentation isolation finding, **not proof of server authorization bypass**.
- Cross-review qualification: the auth reviewer verified that A2's RootSessionHost/MainNavGraph entries are keyed by user ID plus generation, and observed A→B normally destroys the old child ViewModel. Therefore the retained-ViewModel reproduction by itself does **not** prove a currently reachable full-app A→B leak. Track this as local ownership debt/future-reuse risk rather than a demonstrated release blocker; prove a full-root trace before escalating it.

Add a VM zero-photo test requiring zero GPS/status/stash calls and a synthetic failing content-provider test through the picker/read pipeline. Preserve successful fresh check-in controls.

## Unresolved provider and ownership risks — not presented as proven new regressions

- The three order creators now send legacy `payment_capture:1` and comments say this guarantees capture regardless of dashboard settings. Current official Razorpay per-order configuration documents `payment: { capture: "automatic", capture_options: ... }`, while its older official orders docs say `payment_capture` is deprecated. No provider sandbox call or account setting was inspected here, so I cannot prove whether the legacy field is currently honored/ignored for this account. Do **not** accept the claimed override guarantee on this change alone. Both server verify and webhook still accept `authorized` as paid/held; there is no observed reconciler for a never-captured authorization. This high-consequence pre-existing settlement risk remains, and adding a field is not capture confirmation. Official docs also disagree on the authorization deadline between pages; do not freeze the comment's five-day number as an invariant.
  - [Current per-order capture contract](https://razorpay.com/docs/payments/payments/capture-settings/api)
  - [Current account capture settings](https://razorpay.com/docs/payments/payments/capture-settings)
  - [Official older orders documentation noting deprecation](https://d6xcmfyh68wv8.cloudfront.net/docs/api/orders/)
- The payout request uses a deterministic transfer ID, which is the correct direction for retries, but the new code has no executed provider/SQL integration tests in this review. Beneficiary-creation 5xx/network throws still enter the outer catch and record terminal `failed`; only transfer-response5xx gets the new marker. Direct-auth requeue still updates the selected IDs without checking their current claim/terminal state.
- New AMC proof persistence and replay are global, with no account ownership key or request lease. `EquipSevaApplication.kt:81-83` starts the sweep without waiting for the owning auth session. A missing/RLS-hidden status is still treated as safely removable. Server verification does check hospital ownership, so do not describe this as a proven cross-account charge; losing A's recovery marker during unknown/B's auth remains a source-level risk. Broader auth/sync reviewer owns A4/A12 integration.
- `isScopeCancellation` classifies by exception subtype, so an outer timeout is indistinguishable from an internal repository timeout. Add `currentCoroutineContext().ensureActive()` around money follow-up publication/replay before relying on the helper as a complete cancellation fence.
- KYC document paths are now claimed before upsert, correctly preferring an orphan leak to deleting an in-flight server reference. It still uses GlobalScope cleanup and has larger upload/session ownership questions; the seven OTP cancellation failures are not acceptance evidence and were not rerun here.

Neither oversized-provider memory safety nor physical Back/drag/scrim retention was exercised here. Preserve main's decomposed sheets and add actual rendering/gesture tests in the responsible UI slice.
- Assigned Requested jobs now appear in Active Work, which matches `fetchAssignedToMe` filtering on engineer row ID without a status filter. Their detail primary CTA still excludes preassigned Requested jobs (`primaryCtaFor` at2289ff), and check-in only allows Assigned/EnRoute. The patch fixes discovery, not end-to-end handling of every preassigned AMC job. Trace the intended AMC visit action before widening a status gate.
- Chat's restore-draft fix avoids replacing newly typed text but discards the rejected older message if the user has already typed a second draft. An outbox enqueue failure can still unwind before clearing `sending`. These are existing/remaining recovery gaps; pure classifier tests do not exercise storage failure or overlapping composer edits.

## What the source supports

- The old payout 5xx `queued` argument really violates the versioned dispatch contract; the replacement uses a valid status and now reports dispatch-write errors. The terminal/ownership concerns above must accompany that fix.
- `AmcRepository.EdgeFnHttpException` carries actual response status on both RestException and non-success-response paths; the old free-text status test was not a faithful repository contract. Status alone is insufficient for the current server's transient400 responses.
- Fractional SLA input is now rejected by the page gate instead of silently truncated/defaulted. Trim/submit parity is still missing.
- Requested and Disputed assigned jobs are now placed in active/closed lists respectively; unassigned marketplace requests cannot appear via the assigned-to-me query. A live production row was not inspected or independently confirmed here.
- Permanent chat/bid/status errors no longer automatically promise offline delivery; the change uses the common transport predicate. Real network and outbox-storage failures still require integration coverage.
- Photo stashing checks require at least one successful enqueue when the decoded input contains photos; the VM retains open proof sheets on a total stash refusal. Partial success is an explicit accepted policy in the code, not a guarantee that all selected evidence was saved.
- AMC failure outcomes are now collected by the host, not the dismissed payment sheet. ViewModel-owned checkout survives sheet removal; navigation/account/process lifetime is a separate matter. Pending confirmation copy is more honest than generic failure, but currently overpromises automatic recovery in M2.
