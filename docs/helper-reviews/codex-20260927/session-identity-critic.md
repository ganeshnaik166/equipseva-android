Scope: observed session generation, root host lifetime, signup/phone handoff and the cleanup paths this integration invokes. This is **not** a whole-app security score.

**Disposition: HOLD, 8.8/10 for integrated auth/session safety.** The observed A→B, A→signed-out→A, late profile response and host-disposal design is materially stronger: `SessionViewModel.kt:126-174,193-214,243-264` separates observation from I/O and fences profile requests by generation/revision; `RootSessionBoundary.kt:51-94,107-156` keys and obscures account-scoped hosts. The focused tests exercise those properties, including noncooperative profile responses and a delayed preference clear (`SessionIdentityBoundaryTest.kt:118-225,351-370`; `RootSessionBoundaryTest.kt:67-185,222-270`). ## Mandatory blockers before an integrated auth/security acceptance

1. **HIGH — Signup can mutate the next account.** `SignUpScreen.kt:215` keeps the SignIn footer enabled while the form submits. `SignUpViewModel.kt:108-156` resumes an asynchronous A signup and calls `profileRepository.addRole(role)` without binding the operation to A; `SupabaseProfileRepository.kt:186-193` sends only the role to an RPC on the client's then-live auth session. If B signs in before A's result arrives, the pending A workflow can add A's selected role to B, mirror it in shared prefs, and emit a stale route effect. Root callback ownership checks at `AppNavGraph.kt:413-437` occur **after** the backend write and cannot undo it. Test first with a delayed A signup, footer navigation, B sign-in, then A completion; require zero B role/prefs mutation and zero A effect on B. Also test A→out→A with a new login session and a fresh A success. The eventual fix must fence the actual server mutation against the initiating login, not merely the navigation callback; validate the SDK/server ownership contract before implementation.

2. **HIGH — A's admitted cleanup can act on B's global device state.** `SessionViewModel.kt:288-305` checks ownership before and after `signOutCleanup.wipeLocalUserState()`, but `SignOutCleanup.kt:51-90` reads the live token owner and clears global outbox, photo stash, role/onboarding prefs and pending-payment stores without an owner parameter or per-write check. Its `runCatching` wrappers also swallow coroutine cancellation. If A's revoke/cleanup has started and B logs in while it is suspended, cancellation of A's profile job does not prove those later clears belong to A; token revocation can read/delete B's row (`DeviceTokenRegistrar.kt:89-103`). Existing tests at `SessionIdentityBoundaryTest.kt:156-184` cover an A response that arrives **after** B, not cleanup already admitted before B. Add a synthetic noncooperative barrier inside the first cleanup step, switch A→B, release it, and assert no B token/outbox/stash/prefs/payment mutation. The cleanup API needs a captured owner and guards at the actual mutation boundaries (or per-owner storage), plus a separate explicit test for failed/cancelled revoke.

3. **HIGH workflow gap — Hospital signup phone obligation is tied to the current screen.** `authHandoffDestination` blocks a hospital only on `AUTH_SIGN_UP` or unfinished `HOSPITAL_PHONE_ONBOARDING` (`AppNavGraph.kt:265-283`). An in-flight signup can move to SignIn via the enabled footer (`SignUpScreen.kt:215`, `AuthNavGraph.kt:44-50`), then a late validated hospital session on the SignIn route is treated as ordinary sign-in and handed off by `AuthHostInline` (`AppNavGraph.kt:380-402`). `AuthHandoffPolicyTest.kt:28-38` explicitly asserts the ordinary SignIn handoff; it does not model an in-flight signup owner. Track a pending signup/phone obligation for the initiating owner independently of route; test SignUp-submit→SignIn/Back→late hospital confirmation, ordinary hospital sign-in, and A→B replacement. This **proves a dedicated phone-step bypass**, not a proven phone-less Main entry for a normal fresh profile: `Profile.kt:64-80` computes `hasCompletedV2Onboarding` from phone, state and district, and `HospitalOnboardingScreen.kt:55-68,126-145` collects them before Main when incomplete. Do not weaken that server-profile gate when fixing the route flow.

4. **HIGH recovery gap — Confirmed session with no confirmed role has no usable role/recovery surface.** `SessionViewModel.kt:110-121,314-319` correctly sends an unconfirmed role to `NeedsRole`; `AppNavGraph.kt:132-139,175-185` then sends it to `AUTH_GRAPH`. That graph contains Welcome, SignIn, SignUp, ForgotPassword and hospital phone only (`AuthNavGraph.kt:26-75`), with no role picker, explicit sign-out, or retry to finish a failed `addRole`. `SignUpViewModel.kt:129-156` logs an `addRole` failure and still resets/emits the success navigation effect. The result is a signed-in user stranded in auth UI. Add an offline failed-`addRole` test through root composition: require clear retry/role confirmation or sign-out, and require no private host until the server confirms the role.

## Separate limits and follow-ups

- `AuthSession` exposes user ID/email but no opaque login identity; an upstream A→out→A entirely conflated before observation cannot be distinguished from a duplicate (`SessionViewModel.kt:153-165,236-259`). Scope claims must say **observed** boundaries only. A same-user new-session barrier belongs in the repository/server contract.
- During Unknown/revalidation, the prior host is still composed behind an opaque cover (`RootSessionBoundary.kt:121-156`). Touch/semantics tests are useful, but background ViewModel or screen effects can continue; a separate owner-fenced mutation inventory is required. `AppNavGraph.kt:92-103` does not suspend that host.
- The self-profile repository's full-select failure path may return a public minimal profile with `roleConfirmed=false` (`SupabaseProfileRepository.kt:22-79`), which this root classifies as `NeedsRole`; distinguish a transient incomplete fetch from a genuinely unconfirmed role before treating this path as a role decision. Add a synthetic repository+root test for full-select failure/minimal success. The root's first-fetch Retry covers a `Result.failure`, not this successful minimal fallback.
- The deleted-account path sets `revoking=true` before cleanup, and `refreshNow()` refuses revoking sessions (`SessionViewModel.kt:183-190,288-311`). If cleanup stalls or both global/local sign-out fail, the opaque spinner has no retry/sign-out escape. Bound cleanup and surface recovery while keeping the private host closed.
- Singleton buffered deep-link replay and recipient proof are separate A3-02 work; this candidate does not resolve them. Hosted CI, device/TalkBack, real auth-provider behavior and signed release remain unobserved here.
